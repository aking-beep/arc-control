# ARC Control 2.2 — two authorization defects, found from outside

This release fixes two defects in the authorization path. Both were found by
the [Meridian synthetic enterprise](https://github.com/aking-beep/arc-control-sandbox),
an independent harness that drives this product over HTTP, keeps its own
business state, and compares ARC's answers against its own mutation log. Both
were reproducible, both produced real business effects, and neither was visible
to any test in this repository before now.

That is the part worth stating plainly. ARC Control's own suite was green: 616
tests, 76 control-plane properties, and an eval set written specifically to
assert that one authorization produces one effect. It was green because every
one of those tests exercised the paths one call at a time, and both defects
were ordering bugs that only appear when two calls overlap or when time passes
between a decision and its execution. A harness that was not written by the
people who wrote the code found them in an afternoon.

| | Before | After |
| --- | --- | --- |
| Eight simultaneous refunds, one idempotency key | 8 refunds | 1 refund |
| A deny published while an approval was open | `executed` | `denied`, no effect |

---

## Defect 1 — concurrent idempotency

### What happened

The harness sent eight parallel `POST /v1/actions` for the same refund, all
carrying one idempotency key, and counted **eight refunds** in Meridian's own
ledger. Sequential retries were handled correctly, which is why the existing
tests passed.

### Root cause

`Gateway.submit` did two things in sequence:

```
#recordAction(...)   // write the action row
#findReplay(action)  // look for an earlier action with this key *that has evidence*
```

Neither step was wrong on its own. The gap was between them, and it was as wide
as a connector call:

1. Evidence is not written until after the connector returns. That is
   deliberate — the evidence record carries the execution attempt.
2. So `#findReplay` could only ever see a predecessor that had **finished**.
3. Eight concurrent callers each wrote their action row, each looked for a
   finished predecessor, each found none, and each executed.

Replay therefore worked for exactly the case that needs it least — a retry
arriving after the original had completed — and not at all for the case that
causes duplicate effects.

### The fix

`packages/gateway/src/idempotency.ts` introduces an `IdempotencyLedger`. The
claim and the action row are written **in one critical section**, against the
actions collection's own lock:

```
actions.transact(() => {
  find an action with the same (organizationId, agentId, tool, idempotencyKey)
  if found    -> report who holds it
  if not found -> write this action row AND register an in-flight marker
})
```

A caller that does not win the claim never reaches policy evaluation and never
reaches a connector. It is answered one of three ways:

| Situation | Answer |
| --- | --- |
| Same key, **different** parameters | `409 conflict`, refused. Audited. |
| Key held by a request **still running here** | Joins it; returns its result verbatim |
| Key held by a request that **has finished** | Returns the outcome recorded for it |
| Key held, but **no outcome was recorded** | `409 conflict`, refused — never re-executed |

### The semantics this defines

- **One logical action per key, per scope.** The scope is
  `(organizationId, agentId, tool, idempotencyKey)`. Two agents may use
  `retry-1` without colliding; so may one agent across two tools. A key is the
  caller's name for *its own* attempt.
- **One action row per key.** A repeat does not mint a second action, which is
  what keeps "every recorded action has evidence" true — the property
  `ControlAssessment` reads when it reports `actionsMissingEvidence`.
- **A retry sees the latest outcome, not the first.** An action held for
  approval has a `pending_approval` evidence record and, once released, an
  `executed` one. Replay reads the most recent, so a retry after release is not
  told the refund is still waiting on a human.
- **A failed or uncertain execution consumes the key.** The recorded failure is
  returned; ARC does not retry and does not re-execute. For an irreversible
  tool a `failed` outcome does not mean the effect did not land — a connector
  that times out after applying its effect is the documented example — and
  deciding on the caller's behalf that it did not is the one answer that can
  double a refund. A caller who knows the effect did not land presents a **new
  key**.

### The bound on the guarantee — read this before deploying more than one process

`Collection.transact` serializes read-modify-write sequences **within one
process**. Both shipped stores implement it with an in-process mutex:
`MemoryStore` has nowhere else to put it, and `FileStore`'s
`PersistedCollection` wraps the same `MemoryCollection`.

So the guarantee this release makes is precisely: **at most one execution per
idempotency key, per ARC Control process.** Two processes sharing one
`FileStore` directory can both win the claim, and this release does not pretend
otherwise. What it does do is fail safe at the seam — a second process that
finds the key held with no recorded outcome refuses rather than guessing.

Enforcing one execution across processes needs a store whose `transact` is
backed by shared state: a unique constraint on
`(organizationId, agentId, tool, idempotencyKey)` with a conditional insert, a
row lock, or an advisory lock. The `Collection` interface already has the right
shape for it. **No distributed claim is made here, because none has been
tested against a shared persistent store.** This is the same single-writer
boundary the deployment notes already state for the audit chain, and it moves
when a Postgres-backed store lands, not before.

## Defect 2 — execution-time policy revalidation

### What happened

The harness held an $1,850 refund for a finance manager, published an
always-deny policy for `finance.refund`, voted the approval through, and
released it. ARC returned `200 executed` and the customer was refunded — while
an identical *new* request under the same policy was correctly denied. The
engine's strictest-wins rule was working; nothing was asking it.

### Root cause

`Gateway.resume` re-checked three things before releasing: that the grant was
releasable, that the tool's kill switch was off, and that the agent was still
active. It then executed `decision` — the `Decision` row stored when the action
was **submitted**.

An approval is a statement about the past: a human agreed to an action under
the rules in force when they were asked. ARC was treating it as a statement
about the present. Every control that an operator can change while a request
sits in the approval queue — a published deny, a narrowed approver list, a
raised threshold — reached new work and not held work.

### The fix

`#revalidate` runs as the last gate before the grant is spent, and its result
goes into evidence whichever way it falls.

**What it checks**, in this order:

1. **Releasability** — already present: pending, rejected, expired, cancelled
   or already-spent grants are refused on their own terms.
2. **Tool availability** — already present: resolved by name through
   `tools.resolve`, so the kill switch is enforced by the same code the submit
   path uses rather than by a copy.
3. **Agent lifecycle** — already present: the agent must still be `active`,
   which refuses a suspended, retired or draft agent.
4. **Approval binding** — new. The decision must be a decision *about this
   action*, the approval's own record of the agent and tool must match it, and
   the parameters must still hash to the digest the human was shown. The
   action and decision rows are loaded *through* the approval, so comparing
   their ids back to it would be vacuous; what is checkable is whether the
   three rows agree.
5. **Current policy** — new. The policies in force **now** are evaluated
   against this action.

**What it does with the answer:**

| Current policy says | Outcome | Grant |
| --- | --- | --- |
| `ALLOW` | executes | consumed |
| `REQUIRE_APPROVAL`, and the grant on file satisfies it | executes | consumed |
| `REQUIRE_APPROVAL`, narrowed | `pending_approval`, a **new** request opened for whoever policy now names | consumed — it cannot authorize this action, and leaving it live would mint a superseding request on every retry |
| `REQUIRE_APPROVAL` naming nobody | `denied` | **not** consumed |
| `DENY` | `denied`, HTTP 200, with the policy cited | **not** consumed |

A policy denial deliberately does not spend the grant. An operator who
publishes a deny by mistake, or publishes one and then narrows it, should still
have the human decision they already collected.

### Whether a held approval still satisfies a changed requirement

The sound test is not "are these requirements identical" but "would the people
who voted still qualify". ARC records *who* voted — not which selector they
matched, nor which roles they held at the time — so it cannot re-run
`role:finance-manager` against a vote cast last Tuesday.

What it can establish is containment. If every selector the held requirement
admitted is also admitted now, then whoever qualified then qualifies now,
whatever they matched. Formally, the grant carries when all of:

- every selector in the held requirement is admitted by the new one (or the new
  one names `*`);
- the approve-votes on file meet the new `minApprovals`;
- if the new requirement demands separation of duties, the held one did too —
  otherwise the votes on file may include the agent's own owner.

A **relaxed** requirement is satisfied. A **narrowed** one is not, and sends
the action back for a fresh approval. That asymmetry is the control.

### Evaluated as of now, not as of submission

Conditions are re-evaluated against the release-time clock, so
`$.context.hourUtc` and `$.context.dayOfWeekUtc` read *now*. A rule confining
an irreversible tool to business hours is a control over **when the effect
lands**, and re-deciding it against yesterday's clock would void it. An
approval granted at 17:05 for a request submitted at 16:55 is therefore refused
at release under such a rule, and that is the intended reading.

`$.context.source` needed a schema addition to re-evaluate faithfully:
`Action.source` is now recorded (`api`, `mcp`, `cli`, `sdk`, `internal`).
Without it, a rule naming a source would silently stop matching at release —
failing closed, but refusing legitimate releases. Policy replay uses the same
field now, so `simulate` no longer has to state that limitation for actions
recorded by this release or later. The field is optional; for actions recorded
before 2.2 a rule reading `$.context.source` still does not match.

### What this records

A new optional `revalidation` block on the evidence record, covered by the
record's `integrityDigest` like every other field:

```json
{
  "performedAt": "2026-10-26T18:58:14.940Z",
  "effect": "DENY",
  "verdict": "denied",
  "decisionId": "arc_dec_...",
  "policyId": "REFUNDS-FROZEN",
  "ruleId": "freeze",
  "reason": "refunds are suspended pending investigation",
  "agentStatus": "active",
  "toolDisabled": false,
  "approvalBound": true,
  "approvalId": "arc_apr_...",
  "traceDigest": "sha256:..."
}
```

The **original** decision and the full approval history stay exactly where they
were on the record. The second look adds to history; it does not overwrite it.
The fresh decision is stored in full as its own `Decision` row, so the
rule-by-rule path behind a refusal can be read rather than taken on trust.

Two new audit event types: `action.revalidated` on every release, and
`action.replayed` when an idempotency key collapsed a repeat.

### The atomicity limitation that remains

**Revalidation and the connector call are two steps, and nothing here makes
them one.**

The policy snapshot is taken inside `policies.transact`, so a publish part-way
through writing its document and its version record cannot be observed. The
lock is then released before the connector runs, because holding it across a
vendor API call would let one slow connector stall every policy change in the
deployment.

A deny published inside that window — after the snapshot, before the HTTP
request lands — does not stop the call. The window is microseconds of local
work plus the connector's own latency, and it is a genuine gap, not a
theoretical one: a slow vendor widens it.

What ARC does instead of claiming otherwise is record the policy version it
decided against, so the gap is visible in evidence rather than deniable.
Closing it entirely would require the connector to be transactional with the
control plane — a two-phase commit against a third-party API — which ARC cannot
impose and will not simulate.

The same boundary applies to `consume` and the connector: the grant is spent
before the effect, so a crash between the two leaves a consumed approval and no
effect. That is the safe direction, and it is the existing documented choice.

## Defect 3 — retirement was not terminal on every path (ARC-SEC-003)

The Meridian harness revived a retired agent with `POST /v1/agents/:id/activate`.
2.1 routed that endpoint through `registry.activate()`, which refuses a retired
agent, and the harness check passes. Two gaps remained below the route:

- `registry.resume()` and `registry.suspend()` wrote the status with no check,
  so any in-process caller — a seed script, a CLI command, future code —
  could still move a retired agent to `active` or `suspended`.
- `retire()` revoked credentials *before* writing `retired`, and `issueKey()`
  checked the status outside any lock. A key issued in that window survived
  retirement as a live credential. A probe that ran retire and issue
  concurrently left a working key in 50 of 50 rounds.

Every status change now goes through one guarded transition in the registry,
inside the agents transaction, and `retired` is terminal: nothing leaves it,
including a second retirement, which would overwrite `retiredAt`. `retire()`
writes the status first; `issueKey()` checks status and writes the credential
under the same lock, so a concurrent issue either lands before the status write
and is revoked by the sweep, or is refused. Refusals are `409 conflict` with
`details.reason: "agent_retired"`, and `Administration` records each one as an
`agent.transition_refused` audit event. Returning after retirement means
registering a new agent; names stay unique, so it needs a new name.

Behaviour change: retiring an already-retired agent now answers 409 instead of
re-stamping it. The 409 still finishes the credential sweep: a retirement that
wrote its status and then failed before revoking would otherwise leave live
keys that no retry could reach. Whatever the retry revoked is recorded on its
`agent.transition_refused` event as `revokedCredentialIds`.

Tests: `packages/gateway/src/lifecycle.test.ts` (registry and admin paths,
credential issue and rotation, 25 rounds each of concurrent issue-plus-retire
and resume-plus-retire), `apps/control-api/src/lifecycle.test.ts` (all five
routes over HTTP, each refusal audited), and an eval property in
`evals/authorization/identity.eval.mjs`. Five of these tests fail against the
registry before this change.

## What this release does not establish

- **Nothing here makes the platform enterprise-ready**, and no claim in that
  direction should be read into it. Two defects were found from outside and
  fixed; the harness's other findings stand.
- **No distributed concurrency guarantee.** See the bound above.
- **No exactly-once execution.** A connector that times out after applying its
  effect is still recorded as `failed` with the effect uncompensated. That is
  honest and it is not exactly-once. Operator reconciliation remains the
  answer, and it remains manual.
- **The window between revalidation and the connector call is open**, by
  construction.
- **Three further defects in this change were found in review of it**, all in
  what a *refused* release leaves behind rather than in the refusal itself: an
  idempotent retry read `evidence.decision` alone, so it paired
  `outcome: denied` with the submission-time `REQUIRE_APPROVAL` the human was
  asked about and handed back an approval id that was still live; and the
  denial path wrote its evidence without checking that the grant was still
  unspent, so a caller whose revalidation denied could be told `denied` about
  an action a concurrent caller had meanwhile released. Both are fixed, with
  regression cover. The second was ordering-safe in every interleaving that
  could be constructed — the executing path does strictly more work after the
  shared snapshot, so it always wrote last — but that is an accident of await
  counts rather than a property, which is the same way the idempotency defect
  stayed hidden. The third was the same parity bug one layer down: the replay
  rebuilt the decision from the revalidation block, whose `reason` explains why
  the *grant* no longer carried rather than why the rule decided, so a retry
  after a supersession cited the right rule with the wrong text. It now
  summarizes the stored decision, exactly as `resume` does, and the tests
  assert the two field for field rather than field by field — which is what
  let the divergence through in the first place.
- **The 616-tests-green lesson generalizes.** An internal suite is evidence
  about the paths its authors thought to exercise. Where a property matters —
  one effect per authorization, current policy at execution time — it needs an
  adversarial harness that does not share the authors' assumptions, and it
  needs to be driven concurrently. Both of these defects would have survived
  any amount of additional sequential testing.
