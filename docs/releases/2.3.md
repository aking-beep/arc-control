# ARC Control 2.3: five portfolio capabilities, rebuilt as controls

ARC Transformation Group runs free tools that report on parts of the risk ARC Control governs. These are TokenLoop, the MCP Conformance Scanner, Prompt Reviewer, AI Workflow Templates and the Connectivity Scanner. A report can be ignored. 2.3 rebuilds what each one checks as something ARC enforces. The design, the order and the rules every capability follows are in [ADR-0002](../adr/0002-portfolio-capabilities.md). No code was imported from those repositories; each check was reimplemented here with no runtime dependencies.

Every capability is **off until configured**. A deployment that sets nothing decides exactly as 2.2 did.

## 1. Spend control

**What it adds.** Each agent's spend is recorded in a ledger (`packages/spend`). Budgets per agent or per organization, by day or by month, act on that spend when it runs out. They either DENY or REQUIRE_APPROVAL from named approvers, optionally only for `write` and `irreversible` tools.

**How a budget joins a decision.** Budgets are not synthesized into policies. A synthesized policy needs a fallback, and an ALLOW fallback would authorize actions that the default DENY refuses. Instead, `tighten(decision, evaluations)` (`packages/policy-engine/src/tighten.ts`) folds one evaluation per budget into the decision the engine already made:

- it replaces the effect only with a **strictly** stricter one;
- it reads an unrecognised effect as DENY;
- it records every budget evaluation in `evaluations` and `trace`, applied or not, so the evidence shows the budget was checked.

The same fold runs:

- on submission;
- on `explain`, so it says what submission would do;
- at release (`resume`), so a held action whose budget ran out while it waited is re-decided against the budget as it now stands.

If budgets or spend can't be read, the decision is DENY (`budget:unavailable`).

**Spend in policy.** A policy can read `$.agent.spend.dayUsd`, `$.agent.spend.monthUsd`, `$.agent.spend.maxBudgetPercent` and `$.agent.spend.verified`. For example, it can hold actions above 80% of a budget.

**Where spend comes from.**

- *Verified.* `AnthropicCostProvider` reads the Admin API cost report (`GET /v1/organizations/cost_report`). Amounts arrive as decimal strings in cents. The provider fails the whole fetch on a non-USD row, a bad amount, an HTTP error or a cursor that never ends, rather than under-counting. Workspaces are mapped to agents with `ARC_SPEND_ATTRIBUTION`. Spend that isn't mapped still counts toward organization budgets. Re-fetching a day replaces that day's rows rather than adding to them.
- *Reported, unverified.* Operators can record spend (`POST /v1/spend`). Agents can report **their own** spend (`POST /v1/spend/report`). Both are marked `verified: false` and both count, because over-reporting can only tighten. Negative amounts are refused, and a reported record never replaces another one.

**Runaways.** The scheduler's `SpendMonitor` ingests provider spend on each tick. With `ARC_SPEND_SPIKE="multiplier,minimumUsd,baselineDays"` set, it raises a `spend.incident` when an agent's spend today is a spike against its own baseline. With `ARC_SPEND_ON_SPIKE=suspend` set, it also suspends the agent through the audited path. That happens once per agent per day.

**API.**

| Route | Purpose |
| --- | --- |
| `GET`/`POST /v1/budgets` | List and create budgets |
| `PUT /v1/budgets/:id` | Replace a whole budget; the version increments |
| `GET`/`POST /v1/spend` | Read and record spend |
| `POST /v1/spend/report` | The agent route |

Every change is audited: `budget.created`, `budget.updated`, `spend.reported`, `spend.ingested` and `spend.incident`. A budget update records what changed.

## 2. MCP gate at registration

`packages/mcp-security` gains four conformance checks, MCP-CNF-001 to 004, ported from the scanner and run on the manifest:

- the protocol version is reported and recognised;
- tool names are portable;
- input schemas are objects;
- state-changing tools carry a destructive or read-only annotation.

`gradeScan` turns a scan into a letter grade. Any critical finding is an F, and any high finding is no better than a D.

With `ARC_MCP_MIN_GRADE` set, `Administration.registerMcpServer` (`POST /v1/mcp/register`) works like this:

- It **scans the manifest itself**, never a report the caller supplies.
- Every registration must run on that server's connector and name a tool the manifest advertises.
- A server below the minimum registers **none** of its tools.
- Each tool that does register is labelled `mcpGrade` and `mcpFindingsDigest`.
- Registering an MCP tool by itself through `registerTool` is refused.
- Every refusal is audited as `mcp.registration_refused`.
- `POST /v1/mcp/scan` now returns the grade and the minimum in force.

## 3. Prompt review on activation

The new package `packages/prompt-review` is a deterministic, dependency-free port of Prompt Reviewer's static checks. They cover:

- role and objective;
- output contract and delimiters;
- ambiguity;
- instruction priority, trust boundary and untrusted-data framing;
- prompt disclosure;
- embedded credentials;
- refusal and fallback paths;
- a human-confirmation rule when the agent holds state-changing tools.

Any credential pattern, or an empty prompt, grades F.

`POST /v1/agents/:id/prompt-review` returns the full review. The agent record (`promptReview`) and the audit chain keep only the grade, the failed check ids and a `sha256:` digest. **The prompt text is not stored anywhere.** The grade reaches policy as `$.agent.promptGrade`.

With `ARC_PROMPT_MIN_GRADE` set:

- an agent must be registered as a draft;
- activating it is refused, and audited as `agent.activation_refused`, when its review is missing or graded below the minimum;
- the same applies to resuming a suspended agent, so a suspension can't bring an unreviewed agent back.

## 4. Policy packs

`policy-packs/` holds four packs in client-profile format, built from the workflow templates:

| Pack | Rule |
| --- | --- |
| Approval routing | Route and draft; never move money |
| Email | Draft and route; a support lead sends, with separation of duties |
| Meeting to CRM | Propose a diff; a rep confirms; never delete |
| MCP tools by scan grade | Pairs with the MCP gate |

`tools/policy-packs/validate.mjs` loads each pack into a real gateway, using the same validator as client profiles, and checks every scenario's outcome and effect count at the connector. It also requires each pack to:

- use `PACK-` policy ids, so a pack can't overwrite a client's own policy;
- scope every policy with `role:` selectors only, so a pack can't deny or allow beyond the agents it names;
- have no ALLOW fallback;
- include a `pack` block that says where it came from and what to adapt.

`apply.mjs` dry-runs by default. It publishes only through the audited API, and only with `--publish`. A re-apply hits `409` rather than overwriting an operator's edits. Both scripts run in CI and in `npm run harness`.

## 5. Endpoint vetting

`connectors/generic-http/src/vet.ts` reimplements the Connectivity Scanner's checks for a tool's endpoint:

| Check | Refuses |
| --- | --- |
| EP-001 | A non-HTTP scheme, or credentials embedded in the URL |
| EP-002 | A host that does not resolve |
| EP-003 | A metadata host, or any address that is link-local or unspecified, even for a sanctioned host. A private address is allowed only for hosts in `ARC_ENDPOINT_PRIVATE_HOSTS`. IPv4-mapped IPv6 is classified in both forms. |
| EP-004 | Plaintext off loopback |
| EP-005, EP-006 | A certificate that does not verify, or that expires within `ARC_ENDPOINT_MIN_CERT_DAYS` (default 14) |
| EP-007 | A redirect off the host, or down to HTTP |

With `ARC_ENDPOINT_VETTING=true`, a tool with a `connectorConfig.url` that fails is not registered, and the refusal is audited as `tool.registration_refused`. A vetter that throws also refuses. A tool that passes is labelled with when it was vetted and when its certificate expires.

## Behaviour changes

- `scanManifest` runs the new conformance checks, so a manifest with no `protocolVersion` now carries a `low` finding (MCP-CNF-001). `passed` is unchanged, because it still turns only on high and critical findings.
- Decisions can carry evaluations and trace entries whose `policyId` starts with `budget:`. These are not policies.
- `Decision` objects for agents with no budgets are unchanged.
- There is a new error code, `gate_refused` (HTTP 422).
- There are new audit event types, listed above.
- There are new collections, `spend` and `budgets`, and a new optional agent field, `promptReview`. Older data directories open without migration.
- `TickResult` gains `spendIngested` and `spendIncidents`.
- Published schemas:
  - `schemas/agent.schema.json` describes `promptReview`.
  - `schemas/audit.schema.json` lists the 2.3 event types. Its event enum had stopped at 1.0, so the 26 event types added in 2.0 to 2.2 are listed too.

## Security review before merge

`arc-security-reviewer` reviewed the whole diff adversarially and confirmed its findings with probes against the built code. Each fixed finding has a regression test that failed before its fix (`packages/gateway/src/portfolio-review.test.ts` and the tests named in `docs/security/findings.json`).

| Id | Finding | Fix |
| --- | --- | --- |
| ARC-SEC-004 (high) | A per-agent budget for an agent outside the default organization was never enforced, while `GET /v1/budgets` showed it exceeded | A budget naming an agent, and spend naming an agent, take that agent's organization |
| ARC-SEC-005 | Backdated self-reports could pad the spike baseline and disarm the kill switch | Agent reports are dated by the server. Reported spend must fall in the current month. Only verified spend sets the baseline |
| ARC-SEC-006 | One agent could exhaust an organization-wide budget and stop every agent | An agent's report about itself counts toward its own budgets only. Reports must be above zero and are capped at 500 per agent per day |
| ARC-SEC-007 | Credentials in an endpoint URL reached the audit chain on a refused registration | URLs are recorded without credentials or query values, and vetting never echoes them |
| ARC-SEC-008 | A failed MCP batch could leave earlier tools registered | `ToolRegistry.registerAll` validates the whole batch in one critical section before writing any of it |
| ARC-SEC-009 | An active agent whose prompt review fell below the gate stayed active | Such an agent is suspended, and the suspension is audited |
| ARC-SEC-010 | A malformed budget in the store never applied | It now evaluates to DENY. Only an explicit `enabled: false` switches a budget off |
| ARC-SEC-011 | Cost-report edge cases | A missing amount, or a page with no cursor, fails the fetch. Credits are skipped, which over-counts. A batch is checked before any row is written |
| ARC-SEC-012 | The address classifier read IPv4-embedding IPv6 forms (`::a9fe:a9fe`, NAT64, 6to4) as public, and the probe re-resolved DNS | Every embedding form is judged by its IPv4 address, along with 198.18/15 and fec0::/10. The probe's HEAD request is pinned to the vetted address |

Cursor Bugbot then found three more on the pushed branch, all fixed with regression tests:
- A stored budget whose `effects` held invalid values was skipped rather than refused.
- A provider row re-attributed to an agent in another organization was recorded twice.
- Reported spend counted toward today's spike total, so spend that was both reported and ingested from the provider could look like a spike.

The spike rule now compares verified spend only, on both sides.

Two findings are **open**, because they need a design decision rather than a patch:

- **ARC-SEC-013.** When a policy and a budget both require approval, the policy's approvers decide. The approval model can't yet express "one approver from each list", and treating the two lists as alternatives would loosen the requirement.
- **ARC-SEC-014.** `explain`, which an agent key can call, shows budget names and spend positions.

`apply.mjs` also now refuses to send the operator token over plaintext HTTP anywhere but loopback.

## What this release does not establish

- **That a budget bounds spend at its limit.** It refuses the next action once spend has reached the limit, and it is only as fresh as the spend data. Anthropic's cost report is bucketed by day. ARC can't price an action before it runs, so the action that crosses a limit isn't stopped.
- **That reported spend is true.** It is unverified. Over-reporting tightens. Under-reporting, by simply not reporting, is visible only once provider data arrives.
- **That a good grade means safe.** The MCP and prompt grades come from static, pattern-based checks. They raise the floor for what can be registered or activated. A server or prompt that grades A can still be malicious or jailbreakable.
- **That the live MCP server matches the manifest.** Over the API, the manifest is operator-supplied. The MCP connector's manifest pinning, which already existed, is what refuses calls after the live surface drifts.
- **That the running agent uses the reviewed prompt.** ARC sees only the prompt it was given to review. The digest lets a later prompt be compared, but nothing forces the agent's runtime to match it.
- **That a vetted endpoint stays as vetted.** Vetting is a point-in-time check. DNS can change after registration. The connector's allowlist, its HTTPS requirement and its refusal to follow redirects are what hold on every call. The real probe sends one unauthenticated `HEAD` to the endpoint.
- **That a budget's own approvers are always required** (ARC-SEC-013). When a policy already holds the action for approval, the policy's approvers decide.
- **That an MCP grade describes the live server, or a prompt grade the running prompt.** Both grades come from what the operator submits. A check-then-activate race with a concurrent review remains, and agents that were active when the prompt gate was switched on stay active until their next review.
- **That policy simulation sees spend.** Replayed actions are simulated without spend, so rules that read `$.agent.spend.*` don't match in simulation.
- **Anything distributed, or readiness for an enterprise.** Budgets, gates and the ledger hold per process, like the rest of ARC Control. Passing local tests and the Meridian suite is not a production sign-off.
