# ARC Control 2.0

**Released from the 2.0 product specification, October 2026.**

The specification this release implements sets its own boundary, and it is
worth quoting because the rest of this document depends on it:

> P0 — Required for a useful 2.0 pilot
> P1 — Required before broader production commercialization
> P2 — Later expansion if customers validate demand
>
> The distinction matters. ARC Control 2.0 should have a clear release boundary
> rather than becoming a permanently unfinished platform.

**2.0 is the complete P0 set, plus the P1 items that were already code rather
than programmes of work.** What is deferred is listed below with the reason,
because a roadmap that omits the reasons gets re-litigated every quarter.

---

## What 2.0 is

1.0 answered one question: *may this agent do this thing?* It did so with a
gateway, a policy engine, an approval workflow, evidence records and a
hash-chained audit log.

2.0 answers a second: *can you prove the first one worked?*

That is the whole product thesis, and it is why the new module is not a
reporting layer over the old one. A dashboard that counts what the gateway
recorded tells a buyer nothing they could not get from a log search. What they
cannot get anywhere is a control result that states what it examined, over what
window, by what procedure, with what it does **not** establish attached to it —
and an export of the underlying records that verifies with ARC switched off.

### The honesty constraint

Everything in the new module follows from one rule: **a question that cannot be
answered returns `not_assessable`, never `pass`.**

This is not a quality bar, it is the commercial argument. A governance product
that reports green where it has no evidence converts an unexamined risk into a
documented assurance, and the customer finds out when an auditor or an incident
disagrees. At that point the product has not merely failed to help — it has
actively caused harm, and nothing it says afterwards is trusted.

So the vocabulary refuses to express the convenient answer:

| Status | Means |
|---|---|
| `pass` | An automated check ran against real records and the assertion held. |
| `fail` | It ran and the assertion did not hold. |
| `not_assessable` | The question was asked and could not be answered. **Not a near-pass.** |
| `not_applicable` | The scope is empty by design — no MCP tools registered, say. |
| `attested` | A named human stated it, with an expiry. Kept distinct from `pass`. |

Three consequences a reader should expect to see, and which are correct rather
than shortfalls:

**ARC-AI-006 does not pass by default.** The audit chain verifies internally,
but walking records cannot detect truncation — remove entries from the end and
what remains is a shorter, perfectly valid chain. ARC checking its own log
against its own copy of the head proves nothing to a reader who does not trust
ARC. Until the head is anchored outside ARC, the control reports
`not_assessable` and says why.

**ARC-AI-009 can never be automated.** Whether an agent can reach Stripe
without passing through ARC depends on network routes, firewall rules and
credential scope — facts outside ARC's records. It takes a dated attestation
from a named reviewer, reports `attested`, and reverts to `not_assessable` when
that attestation expires rather than carrying the old answer forward.

**A fresh install reports mostly `not_assessable`.** It has no traffic, so
there is nothing to assess. The alternative — reporting an empty deployment as
healthy — is the single most dangerous thing this module could do.

### No percentages

Nothing in 2.0 emits a coverage percentage or a compliance score, and a test
asserts it across every governance page. A single number invites a target, a
target invites gaming it, and "94% covered" tells a reader nothing about
whether the missing 6% is a dormant test agent or the one holding production
database credentials. Coverage analysis lists the gaps by name instead.

### Framework mappings ship unreviewed, on purpose

The NIST AI RMF mappings cover all four functions and every one ships as
`proposed`, not `reviewed`. ARC's engineering team can draft a mapping; only
someone accountable for the customer's compliance programme can accept one.
A framework table marked reviewed at the factory is precisely the artefact that
ends up in a board pack. Coverage counts only reviewed mappings, so the figure
starts at zero and rises as real review happens.

## What shipped, against the specification

### 01 · Agent identity, inventory and lifecycle

| | |
|---|---|
| Enriched agent inventory | `AgentGovernance`: purpose, department, criticality, deployment reference, data classification, review cadence. Optional, so an agent registered by 1.x has none — and coverage reports that as a gap rather than synthesising a default. |
| Agent-to-tool permissions | The Access matrix, from 1.0, unchanged and still correct. |
| Agent lifecycle | `draft` → `active` → `suspended` / `retired`. Retiring revokes every credential and cannot be undone. |
| Credential inventory | State resolved (`active` / `expiring` / `expired` / `revoked`), days to expiry, and a never-used flag — an unused key usually means it leaked or was forgotten. |
| Credential rotation *(P1)* | Issues before revoking, so a routine rotation does not fail an agent mid-run. |

**One security fix this forced.** Authentication asked "is this agent
suspended?". Adding `draft` and `retired` would have let both act — a draft
agent before it was cleared, a retired one after it was withdrawn. It now asks
"is it active?", which fails closed for any state added later.

### 02 · Authorization, policy and action control

| | |
|---|---|
| Policy coverage analysis | Every high-impact tool × active agent pair, using the gateway's own selector logic so coverage cannot disagree with enforcement about what a policy matches. |
| Policy simulation | A hypothetical action, or a replay of recorded traffic. Writes nothing, executes nothing — pinned by a test that snapshots every collection count and the audit length around both calls. |
| Policy version history | Each publish appends the full document alongside the one it replaced, with a structural diff and the publisher. 1.0 claimed policies were versioned but kept only the current one, so "explain version 3" worked until somebody published version 4. |
| Approval verification | ARC-AI-004: approval exists, reached approved, met the minimum, every vote preceded execution, separation of duties honoured, approval consumed. |
| Gateway bypass assessment | ARC-AI-009, attestation-based. See above. |

### 03 · Runtime security

| | |
|---|---|
| Action risk classification | Deterministic, from the tool's declared effect and tier plus parameter signals. Exposed to policy as `$.action.risk.*`; **nothing consults it to permit anything**. One authorization path, still. |
| Expanded kill switches | Per-tool and per-connector, refused at resolution before any policy is consulted — a test asserts an allow-everything policy cannot run a disabled tool and that no decision is even reached. |
| Sensitive action protection | Via classification plus policy, rather than a second hard-coded path. |
| Rate and execution limits *(P1)* | A safety valve, not a quota. Counts recorded actions so it survives restart; off unless configured; a refused action is not recorded, so one runaway cannot lock itself out. |

The monetary escalation threshold has **no default**. ARC cannot know whether
500 is a lot for a given organization, and a made-up number would make the
classifier confidently wrong for everyone it does not fit.

### 04 · MCP and integrations

Carried forward from 1.0: the MCP gateway, manifest scanning, drift detection,
schema validation, pinning. ARC-AI-007 now asserts that every MCP-backed tool
pins a manifest digest, and reports `not_applicable` where none is registered.

Deliberately **not** expanded: the specification's own advice is that "two
deeply tested integrations are more valuable than fifteen shallow
demonstrations", and nothing in a pilot justifies building the other thirteen.

### 05 · ARC Assurance

The new module. Control library, nine ARC-AI controls with deterministic
evaluators, assessment runs persisted with their window and inputs, a findings
register reconciled across runs, a risk register, coverage analysis, and
automated-versus-attested classification throughout.

**Findings are reconciled, not replaced.** A repeat increments its occurrence
count; a subject that stops failing is resolved with the assessment that
cleared it named. Replacing the register each run would destroy the remediation
history, which is the part customers actually care about.

**Residual risk is never computed.** Crediting a control automatically would
mean the platform grading its own homework — the number would improve because a
control exists, not because anyone checked it works. It is absent until a named
human reviews it, with their rationale stored beside it.

### 06 · Compliance evidence

Evidence bundles carry the primary records, each with its expected digest, and
verify by recomputation with no store, no network and no ARC instance. A test
round-trips through JSON to prove it.

Evidence and assessments carry **two** digests: the bundle digest catches
alteration after export, and the record's own integrity digest — written when
ARC stored it — catches alteration *before* export that a recomputed bundle
digest would have accepted. The walkthrough demonstrates exactly that attack
being caught.

`failures` and `limitations` stay separate on every verification result. An
intact bundle with no external anchor is valid *and* limited; telling someone
their evidence was tampered with when it merely cannot rule out truncation
would destroy their trust in the tool that told them.

### 07 · Observability

Action timeline, policy decision analytics with explicit windows, per-agent
activity, control evaluation history. OpenTelemetry and SIEM export are P1 and
deferred — see below.

### 08 · Enterprise security

| | |
|---|---|
| No agent access to governance administration | Every one of the 35 governance routes is operator-only. A test presents a **valid** agent API key to all of them and asserts 401, with the route list written longhand so a route added later cannot escape it. |
| All administrator changes audited | Risks, controls, findings, attestations, kill switches, lifecycle changes, bundle exports. |
| Secured pilot deployment | Documented, with its limits stated rather than softened. |

**The honest limitation, stated in the product and not only here.** Operator
identity is a configured request header behind a single shared token. Anyone
holding that token can claim any identity, so an approval establishes that the
workflow ran — **not who ran it**. The Settings page says this in those words,
ARC-AI-004 carries it as a stated limitation, and every evidence bundle
carries it too. SSO and RBAC are the next release.

### 09 · Console

Five new sections — Assurance, Risks, Findings, Activity, Settings — plus
detail pages for controls, assessments, runs, risks, findings and framework
mappings. Still server-rendered, still zero client JavaScript, still
`default-src 'none'`.

Tools, Access and Audit were not in the 2.0 proposal and were kept anyway: each
is a working page with tests and a place in the published showcase, and
removing a working answer to "what can this agent reach?" to hit a nav count
would be a loss rather than a tidy-up.

### 10 · Developer experience

Assurance API (35 routes), typed SDK methods for all of them, and four CLI
commands that need no running server: `arc assurance controls`,
`arc assurance evaluate`, `arc assurance coverage`, `arc bundle verify`.

`arc assurance evaluate` exits 1 on a control failure and deliberately **not**
on `not_assessable`: gating CI on a question ARC could not answer makes the
gate either useless or permanently red.

### 11 · Infrastructure

Reproducible local install, Docker and Kubernetes manifests, persistent
assurance storage, explicit fail-closed behaviour, health checks that separate
enforcement from assurance, and backup/restore documented in
[OPERATIONS.md](../OPERATIONS.md).

`/health/enforcement` reads nothing from the assurance layer, so a load
balancer has something that cannot be turned red by a stale control
assessment. The fail-closed invariant is tested by *actually breaking*
assurance — every assurance collection swapped for a proxy that throws — and
asserting the gateway still allows what policy allows and denies what it
denies.

### 12 · Commercial readiness

Not code. See [COMMERCIAL_READINESS.md](../COMMERCIAL_READINESS.md) for the
ideal customer, the differentiation argument, the pricing hypothesis and the
design-partner material, and [SECURITY_QUESTIONNAIRE.md](../SECURITY_QUESTIONNAIRE.md)
for buyer technical evaluation.

## What is deferred, and why

Nothing below is implemented. It is listed so that a reader can tell the
difference between a decision and an oversight.

### P1 — before broader commercialization

| | Why it is not in 2.0 |
|---|---|
| **SSO (OIDC)** | A real identity integration, not a feature flag. It replaces `operator.ts` entirely, and shipping a half version would mean two authentication paths. |
| **RBAC** | Depends on SSO: roles without authenticated identities are decoration. The capability boundary that *does* exist — agents cannot reach governance at all — is implemented and tested. |
| **Separation of duties across GRC** | Needs RBAC to be meaningful. Enforced today only where policy demands it on an approval. |
| **PostgreSQL / concurrent durable store** | The storage contract is implemented twice already (memory, append-only file), so a third is mechanical — but it needs migration tooling, connection management and a concurrency test suite that is its own project. The file store is honest about being single-node. |
| **High availability** | Follows the database. Doing it on the file store would be a lie. |
| **OpenTelemetry / SIEM export** | Both are small once the trace model is settled, and the trace model should be settled by a design partner's existing stack rather than guessed. |
| **Python SDK** | Mechanical given the published schemas, and worth doing when a customer asks in Python. |
| **Terraform provider** | P2 in the specification; listed here because it is often asked for early. |
| **External integrity anchoring** | The *model* is implemented — bundles take an anchor, ARC-AI-006 distinguishes anchored from not. What is missing is the scheduled job that writes the head somewhere ARC cannot reach, which needs a target the customer chooses. |
| **Penetration testing** | A service, not a commit. |
| **Prompt/tool-injection testing** | Partly covered by the existing MCP scanner and the eval suite's poisoning cases; a full harness is its own effort. |
| **EU AI Act / ISO 42001 mappings** | Deliberately not shipped as data. Publishing an unreviewed mapping table for a framework with legal consequences invites someone to rely on it. |

### P2 — only if customers validate demand

Agent discovery, delegated agent permissions, cross-agent attack monitoring,
connector marketplace, third-party vendor assessments, customer trust portal,
cost attribution, anomaly detection, SCIM, full multi-tenant SaaS
administration, multi-region.

Anomaly detection and cost attribution are listed last on purpose: both need
real operational data to be anything other than a plausible-looking chart.

## Upgrading from 1.x

```bash
npm install && npm run build && npm run verify
```

**Data.** A 1.x data directory opens without migration. Every field added to an
existing object is optional, the new collections start empty, and the directory
is stamped with the model version on open. A 1.x build reading a 2.0 directory
ignores the files it does not recognise, so the upgrade is reversible.

**Behaviour.** Three changes a 1.x deployment will notice:

1. Agent authentication now requires status `active` rather than merely
   not-suspended. No existing agent is affected: 1.x could only produce
   `active` or `suspended`.
2. The API version string is `2.0.0`, and `/health` gained `enforcement` and
   `assurance` objects. Existing fields are unchanged, so an existing health
   check keeps working.
3. The baseline control library installs on API start. Idempotent and
   non-destructive — a control an operator disables or retunes keeps those
   edits across restarts.

**Contracts.** Every schema `$id` moved from `v0.1` to `v2.0`. Four new
schemas; three existing ones were corrected to describe fields the model had
already gained. See [schemas/README.md](../../schemas/README.md).

**Not required, but the first thing to do.** Record a governance record for
each agent and a permission review, or ARC-AI-001 and ARC-AI-008 will fail —
correctly. They are failing because nobody has recorded who owns these agents,
which is worth knowing.

```
356 tests          node --test across every package
66/66 properties   npm run evals
14 steps           node examples/console-walkthrough/run.js

```

The eval suite is the artefact to read first. It asserts the product's claims
in terms a reviewer can check without reading the implementation — including
every honesty invariant above, each one failing loudly if the behaviour
regresses.
