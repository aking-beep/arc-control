# ARC Control 2.1 — the commercial release

2.0 was a complete governance model with three gaps that stopped it being
something you could sell to a company of ten to a hundred people and support.
This release closes them.

The gaps were not features anybody forgot. Each was a deliberate deferral in
2.0, stated in that release's own notes, and each turned out to be load-bearing
for the commercial case rather than a nicety:

1. **Operator identity was a request header behind a shared token.** The
   product said so honestly, which was right and no use at all to a buyer whose
   reason for wanting ARC was the audit trail.
2. **Nothing was ever sent anywhere.** The console told operators, in those
   words, that the page was the notification. For a workflow with a human in it
   that is the difference between a control and an obstacle.
3. **Every write rewrote a whole collection file.** Fine for a demo; the cost
   of recording an action grew with every action already recorded.

---

## What shipped

### Individual authentication, and the provenance of every name

OpenID Connect single sign-on: authorization code with PKCE, ID token
signatures verified against the provider's published keys, server-side sessions
with an idle timeout, and roles taken from verified claims rather than from a
request header — so a signed-in operator cannot widen their own authority.

**Adding sign-on alone would not have been enough**, and this is the part worth
reading. A real deployment is mixed: a console session, a CI job behind a
proxy, an automation still holding the legacy token during migration. If all
three produced the same record, a reader could not tell a verified approval
from an asserted one, and the strongest claim the whole set could support would
be its weakest member. So the provenance of an identity is recorded alongside
it — `authenticated`, `asserted_by_proxy` or `claimed` — on the vote, in the
evidence export and in the audit chain.

That is what lets **ARC-AI-004 report the truth about a specific deployment**
rather than carrying a caveat written for all of them. A deployment on single
sign-on earns "these approvals are attributable to individuals", naming the
issuer. One still on the token is told how many votes it cannot attribute and
why. A mixed window is counted honestly rather than rounded up. A vote recorded
before 2.1 reads as `claimed`, because that is what the deployment which wrote
it could support.

Roles can come from provider groups **or** from a list of named people, because
a ten-person company often has no group management and supporting only the
first would make this unsellable to the smaller half of the range.

The shared token survives as a **fallback, never a bypass**: it keeps working
when it is the only mode configured, so upgrading a 2.0 install does not lock
its operators out, and it stops being accepted the moment a real mode is
configured.

### Notification, and a record of what was not delivered

Outbound delivery over `fetch`, with no new dependencies. One rule shapes it:
**a delivery that failed is not a notification.** Fire-and-forget to a webhook
is worse than no webhook, because it creates the belief that somebody was told.
The record is written before the request, every attempt is recorded with its
status, and a failing channel is listed — so the platform can say "nobody was
told" as plainly as it says "nobody approved".

A notification leaves the trust boundary, so the default payload carries
metadata and a link and **no action parameters at all**. Redacted is not the
same as safe to post in a chat workspace: a tool name, an amount and a customer
reference together are a disclosure with every secret already removed.

### The unattended half

A scheduler warns before an approval window closes, lapses the windows that
have, assesses controls on their own interval, notifies about overdue findings,
retries deliveries and prunes dead sessions. Until now a lapsed approval only
became `expired` when something touched it, so an abandoned request sat reading
`pending` and the console showed it as live work.

Its rule is that **a run that failed must not look like a run that passed**.
Each step's failure is collected and named rather than thrown, so a broken
webhook cannot stop approvals from lapsing; a pass with problems is written
into the audit chain, because a scheduler that quietly stops working looks
exactly like one with nothing to do.

### Storage that does not get slower

Every collection is now an append-only log, compacted once it holds more dead
weight than live records. A put appends the record exactly as the old format
stored it, so an existing 2.0 data directory loads unchanged.

Measured on a single container:

| Records | Write time | Per record | File | Reopen |
|---|---|---|---|---|
| 1,000 | 342ms | 342µs | 0.3MB | 14ms |
| 5,000 | 1.6s | 319µs | 1.3MB | 41ms |
| 20,000 | 5.4s | 268µs | 5.3MB | 102ms |

Per-record cost is flat. One governed action writes about five records, so this
is on the order of 700 actions per second against a few hundred to a few
thousand per day for a company in this range.

### Operability

Configuration is validated before anything is opened, and **ARC refuses to
start** in configurations that would run but should not: single sign-on with no
session secret, a secret too short to sign with, insecure cookies on a
non-loopback bind, a port that is not a port. Every refusal names the variable
that resolves it, and all of them are listed at once.

A token-only deployment on a non-loopback interface warns loudly rather than
refusing. That one started as a refusal and it was the wrong signal: a
container must bind `0.0.0.0`, so it tripped every containerized deployment
including this repository's own image. Refusing on a signal that cannot tell
`docker run` from an open port teaches people to set the override reflexively,
after which the override means nothing.

`arc backup create` and `arc backup verify` copy a data directory with
per-file digests and then check them and the audit chain inside the copy. A
backup nobody has verified is a belief about a backup. Verification is
read-only, which is the same property that lets an auditor check an evidence
bundle without altering it.

`/health/ready` answers "should traffic come here" with a real read against the
store, distinct from `/health`'s liveness.

## What is deliberately still not here

Stated with the reason, as in 2.0, because a list of gaps without reasons is a
roadmap and a list with them is a decision.

**More than one writer.** `transact` is an in-process mutex, so exactly one
process may write: two replicas would break the single-use approval guarantee
and the audit chain's single-writer assumption. This is the real ceiling, and
it is deliberate for this range rather than an oversight — a single well-run
node with a volume and verified backups is the right architecture for ten to a
hundred people, and building a clustered store before a customer needs one
would be guessing at their shape. A Postgres-backed store with a cross-process
lock and the chain anchored externally is the first thing to build when
somebody outgrows this, and it is not built.

**Per-object RBAC.** Roles gate who may approve what, through policy approver
selectors. There is no per-object permission model and no delegation. The
boundary that exists and is absolute is between agents and operators.

**Email and paging.** Notifications reach a webhook or a chat workspace and no
further. Both of those a customer already has; an on-call integration is a
choice about their rota, not ours, and inventing one before a design partner
names it would be guessing.

**External anchoring as a scheduled job.** ARC-AI-006 still reports
`not_assessable` by default, and that remains correct: ARC checking its own log
against its own copy of the head proves nothing to a reader who does not trust
ARC. Anchor the head somewhere you control and it passes.

**A penetration test.** Not a commit.

**Self-serve signup and billing.** Not built, and not the right thing to build
for this buyer: a company of this size is invoiced after a conversation. The
install is a container, a volume and a dozen environment variables, which is
the shape that actually matters.

## Upgrading from 2.0

Nothing is required. A 2.0 data directory loads unchanged, the shared token
keeps working while it is the only mode configured, and the scheduler is on by
default.

To get the thing this release exists for, set `ARC_OIDC_ISSUER`,
`ARC_OIDC_CLIENT_ID`, `ARC_OIDC_REDIRECT_URI` and `ARC_SESSION_SECRET`, then
map roles with `ARC_OIDC_ROLE_MAP` or `ARC_OPERATOR_DIRECTORY`. Startup will
tell you if you have configured sign-on but no roles, which would let everyone
in and let nobody approve anything. See `docs/OPERATIONS.md`.

Two behaviour changes to know about:

- Configuring single sign-on or a trusted proxy **stops the shared token being
  accepted**. Set `ARC_ALLOW_SHARED_TOKEN=true` if you need both during a
  migration.
- A token-only deployment on a non-loopback interface now warns at startup.
  It still starts.
